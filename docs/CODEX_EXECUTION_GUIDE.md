# 使用Codex开发医药雷达

版本：1.0  
目的：将PRD转换为可审查、可测试、可逐步完成的Codex任务

## 1. 为什么这样组织

复杂项目不适合用一句“把整个App写完”交给Codex。每个任务应明确：目标、上下文、约束和完成条件，并要求Codex运行测试、检查差异和说明风险。

仓库根目录`AGENTS.md`保存长期有效的工程规则；`CURRENT_PHASE.md`限定当前版本；三个PRD分别定义范围和验收。不要把全部PRD正文重复粘贴到每次提示中。

## 2. Codex启动提示词

在空仓库放入本规格包后，发送：

```text
请先阅读仓库根目录AGENTS.md、docs/CURRENT_PHASE.md、当前阶段PRD以及docs/ARCHITECTURE_AND_MIGRATION.md。

当前任务只做规划，不写代码：
1. 总结V1.0目标、P0范围、非目标和关键风险；
2. 检查文档之间是否存在冲突或阻塞开发的歧义；
3. 按依赖顺序把V1拆成可单独测试、可单独提交的任务，每个任务关联需求ID；
4. 给出预计创建的目录和文件；
5. 给出每个任务的测试命令和完成条件；
6. 不得计划V2或V3功能。

如果存在会显著改变架构、成本、合规或功能范围的问题，先问我；其他细节作最小合理假设并记录。
```

确认计划后，再让Codex开始实现。

## 3. V1建议任务提示词

以下提示词按顺序逐个发送。不要一次发送全部任务。

### V1-任务1：仓库骨架

```text
实现V1 Epic 1的仓库骨架，只完成工程初始化和可运行的最小页面/最小Java命令，不实现真实采集和业务页面。

上下文：AGENTS.md、docs/CURRENT_PHASE.md、docs/PRD_V1_PERSONAL_STATIC.md、docs/ARCHITECTURE_AND_MIGRATION.md。

要求：
- frontend使用Vue 3 + TypeScript + Vite；
- backend使用Java 17、Maven Wrapper和多模块结构；
- 创建contracts、config、data/fixtures、infra、docs需要的目录；
- 前端使用pnpm并锁定`pnpm-lock.yaml`，配置前后端lint、单元测试和构建；
- 添加根README，写清Windows PowerShell和常见shell的运行方法；
- 不添加MySQL、登录、Spring MVC常驻服务或云服务器配置。

完成时：运行所有可用测试和构建，列出文件、命令、结果、未解决问题，并更新CURRENT_PHASE对应清单。
```

### V1-任务2：数据契约

```text
实现V1数据契约，覆盖V1-F-012及第6节。

交付：
- contracts/article.schema.json
- contracts/feed.schema.json
- contracts/source-health.schema.json
- 有效和无效fixture
- Java领域对象及序列化测试
- TypeScript类型及Schema验证测试
- schemaVersion兼容规则说明

严格采用ARCHITECTURE_AND_MIGRATION.md中的稳定字段。不要加入数据库/JPA。完成前运行后端测试、前端测试和Schema校验。
```

### V1-任务3：来源框架与首批连接器

```text
实现V1-F-008、V1-F-009和V1-F-014。

先检查各来源是否有官方API/RSS和使用条件，再选择首批6个连接器，覆盖国内外、监管、临床试验、科研和企业/交易所类别。把选择和理由记录到docs/SOURCES.md。

要求：
- SourceConnector统一接口；
- RSS、REST、HTML列表三类基础实现；
- config/sources.yml；
- 连接/读取超时、有限重试、User-Agent和来源级错误；
- 测试只使用fixture或Mock服务器，不依赖实时网络；
- 不绕过登录、验证码、付费墙、robots或反爬；
- 单源失败不终止批次。

如果某个来源是否合法或是否允许自动访问不明确，先停用该来源并记录，不要猜测。
```

### V1-任务4：规范化、去重、分类和排序

```text
实现V1-F-003、V1-F-010以及Article分类规则。

要求：
- URL规范化、标题规范化、稳定ID和内容哈希；
- 同来源与跨来源去重；
- 保留一个主条目和全部来源链接；
- 12个一级栏目、地区和事件枚举；
- 可解释的重要度打分和今日必读选择；
- 使用代表性fixture覆盖中英文、缺失日期、相似标题和冲突来源；
- 不能确认时不得误合并。

完成时给出去重测试数据和结果摘要。
```

### V1-任务5：翻译、摘要与静态导出

```text
实现V1-F-011、V1-F-012。

要求：
- TranslationProvider和SummaryProvider接口；
- 无付费密钥时可运行的降级实现；
- 可选外部Provider必须由环境变量显式启用；
- 输出generated、generatorVersion和生成时间；
- 生成失败不得阻止文章发布；
- 摘要不得编造、不得提供医疗或投资建议；
- 输出manifest、latest、daily、taxonomy、source-health；
- 每个输出通过Schema校验并有SHA-256；
- 不导出第三方全文、秘密或调试堆栈。

先用fixture完成端到端静态导出测试。
```

### V1-任务6：PWA页面

```text
实现V1-F-001至V1-F-007的前端P0。

页面：今日、分类、详情、关注、收藏、设置。

要求：
- 使用ArticleRepository抽象和StaticArticleRepository；
- mobile-first，覆盖360/390/430px；
- iOS安全区域和Android返回流程；
- 搜索、组合筛选、稳定排序；
- IndexedDB收藏/关注/已读以及导出导入；
- 空、错、慢、离线、过期数据状态；
- PWA安装和更新提示；
- 不从外部CDN加载关键资源；
- 单元测试和关键组件测试。

请先实现功能和可访问性，再做克制的视觉完善。不要实现登录或API模式。
```

### V1-任务7：GitHub自动化

```text
实现V1-F-013及自动部署。

要求：
- ci.yml：前后端测试、Schema校验、构建；
- collect.yml：定时与手动采集、并发控制、产物验证；
- deploy-pages.yml：只部署验证通过的静态产物；
- 失败不覆盖上一版站点；
- 敏感配置只从GitHub Secrets读取；
- 记录手动回滚步骤；
- 不提交真实密钥。

使用本地可验证方式测试workflow语法和脚本；无法真实部署时明确列出需要我在GitHub执行的步骤。
```

### V1-任务8：最终验收

```text
按照PRD V1第9节和第11节进行完整验收，不新增范围外功能。

执行：
- 所有lint、单元、集成、Schema、构建和E2E；
- 检查密钥、第三方全文、大文件和生成垃圾；
- 检查iPhone Safari与Android Chrome人工测试清单；
- 检查来源追溯、数据过期、离线和失败降级；
- 审查未完成TODO和跳过测试；
- 对未满足项给出修复并重新验证；
- 更新CURRENT_PHASE和README。

最后按需求ID输出通过/失败/未测试矩阵。不要把未运行项目标记为通过。
```

## 4. 切换到V2

V1观察期通过后，发送：

```text
请先只评估V1进入V2的准备情况，不写代码。阅读CURRENT_PHASE、V1/V2 PRD和迁移规范，逐项检查V1升V2门槛，输出：已满足、未满足、需要我确认。重点检查自托管设备、Tailscale用户范围、V1数据导入、MySQL备份恢复和公网端口风险。只有我明确批准后，才能把CURRENT_PHASE改为V2.0。
```

批准后再发送：

```text
我批准进入V2.0。请更新CURRENT_PHASE，然后只为V2 P0生成按Epic拆分的实施计划。每个任务关联V2需求ID、迁移步骤、测试和回滚方式。不得开放公网，不得实现V3注册和生产云能力。
```

## 5. 切换到V3

进入V3前发送：

```text
请对照PRD V3第2节做上线门禁评估，只生成检查报告，不部署、不购买资源、不修改DNS、不开放公网。技术检查可以执行；法律、许可、版权和运营主体事项必须标记为需要人工/专业确认，不得自行判断为通过。
```

人工批准后：

```text
根据已批准的V3上线范围，生成V3 P0实施计划。只实现匿名只读公开版和明确批准的基础设施。注册、通知和P1/P2能力不在本轮范围。每一步必须包含staging验证、数据库迁移、回滚、安全检查和监控验收。
```

## 6. 日常功能提示词模板

```text
目标：实现/修复【需求ID和一句话目标】。

上下文：
- 阅读AGENTS.md、CURRENT_PHASE和【PRD章节】；
- 重点文件：【文件或目录】；
- 当前现象/错误：【如有】。

约束：
- 只修改当前目标所需范围；
- 保持Article/API契约兼容；
- 不添加未批准生产依赖；
- 不处理下一版本功能。

完成条件：
- 【可观察行为】；
- 新增或更新测试；
- 运行【命令】并通过；
- 汇报改动、测试、风险和未完成项。
```

## 7. Bug提示词模板

```text
请诊断并修复【问题】。

重现步骤：【步骤】
预期结果：【结果】
实际结果：【结果/日志】

先复现或用测试证明问题，再定位根因。添加能在修复前失败、修复后通过的回归测试。不要顺便重构无关代码。完成后运行相关测试并说明根因、修改、验证和剩余风险。
```

## 8. 审查提示词

```text
请审查当前未提交更改，重点检查：
1. 是否违反当前阶段范围；
2. Article/Feed/API兼容性；
3. 来源追溯、版权边界和生成内容标识；
4. 鉴权、越权、SSRF、密钥和日志泄漏；
5. iOS/Android移动端回归；
6. 测试缺口和部署回滚。

先列发现，按严重程度排序并引用文件位置；没有发现时明确说明仍未覆盖的测试风险。不要在我确认前大范围改写。
```

## 9. 与Codex协作规则

- 一个聊天尽量对应一个清晰任务或Epic；
- 复杂任务先用Plan模式；
- 提供错误日志原文，不只说“不能运行”；
- 每次查看Codex生成的diff；
- 每个阶段建立Git标签或发布点；
- 重要迁移前创建可恢复备份；
- Codex提出购买服务、开放公网、处理真实用户数据或使用新来源时，必须由你确认；
- Codex无法运行真实设备、GitHub或云环境测试时，由你执行其给出的最小人工步骤，并把结果反馈回同一任务。
